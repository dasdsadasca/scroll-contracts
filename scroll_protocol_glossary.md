# Scroll Protocol Glossary

| Term                             | Definition                                                                                                                                                                                                                            |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Core Rollup & State**          |                                                                                                                                                                                                                                       |
| ScrollChain                      | The L1 smart contract that manages the state of the Scroll L2 rollup. It receives L2 batch commitments, verifies ZK proofs, finalizes batches, and interacts with the L1 message queues.                                             |
| Batch (L2 Batch)                 | A collection of L2 transactions bundled together by a Sequencer, along with metadata (like parent hash, L1 message data, data hash/blob reference). Batches are committed to L1 and then proven.                                       |
| Chunk (within a Batch)           | A segment of an L2 batch, containing a sequence of L2 blocks and their transactions. Used in older batch versions (pre-V7) to organize data committed to L1.                                                                           |
| Validity Proof (ZK Proof)        | A cryptographic proof (specifically a Zero-Knowledge proof) generated by Provers that attests to the correctness of L2 state transitions within a batch or bundle of batches, without revealing the full transaction data.                 |
| State Root                       | A Merkle root representing the state of the L2 chain at a specific point (e.g., after a batch is executed). Finalized state roots are stored in `ScrollChain`.                                                                      |
| Withdraw Root (Message Root on L2) | A Merkle root representing all L2-to-L1 messages sent within a specific L2 batch. This root is included in the batch header submitted to `ScrollChain` and is used to prove message inclusion on L1. Generated by `L2MessageQueue`. |
| Rollup                           | A Layer 2 scaling solution that executes transactions off-chain (on L2), bundles them, and posts compressed data and proofs to a Layer 1 blockchain (Ethereum) for security and finality. Scroll is a zk-Rollup.                   |
| zkEVM                            | Zero-Knowledge Ethereum Virtual Machine. An EVM-compatible virtual machine that can generate ZK proofs for its computations, allowing Scroll to prove L2 state transitions to L1.                                                      |
| **Actors & Roles**               |                                                                                                                                                                                                                                       |
| Sequencer                        | An entity responsible for collecting L2 transactions, ordering them, executing them, and submitting L2 batches (or their commitments) to the `ScrollChain` contract on L1.                                                            |
| Prover                           | An entity responsible for generating ZK validity proofs for the L2 batches committed by Sequencers. These proofs are then submitted to `ScrollChain` for verification.                                                               |
| Relayer                          | An off-chain actor that facilitates cross-domain communication by submitting messages and proofs. For example, relaying an L2->L1 message with its proof to `L1ScrollMessenger`.                                                      |
| Keeper                           | An off-chain actor responsible for triggering specific automated tasks, such as executing a batch deposit in `L1BatchBridgeGateway` or distributing tokens in `L2BatchBridgeGateway`.                                                  |
| **Messaging Infrastructure**     |                                                                                                                                                                                                                                       |
| L1ScrollMessenger                | The L1 contract that facilitates L1->L2 and L2->L1 messaging. It sends L1->L2 messages to an `L1MessageQueue` and relays L2->L1 messages (with proof) to their L1 targets. Handles message replays and drops.                       |
| L2ScrollMessenger                | The L2 predeployed contract that facilitates L1->L2 and L2->L1 messaging on the L2 side. It relays L1->L2 messages to their L2 targets and sends L2->L1 messages to `L2MessageQueue`.                                                 |
| L1MessageQueueV1                 | The legacy L1 contract used to queue L1->L2 messages before the EuclidV2 upgrade. It managed message hashes, skipped messages, and finalization status in coordination with `ScrollChain`.                                            |
| L1MessageQueueV2                 | The current L1 contract used to queue L1->L2 messages. It incorporates a rolling hash of messages (used in ZK proofs) and enqueue timestamps. Does not support "skipped" messages in the same way as V1.                            |
| L2MessageQueue                   | The L2 predeployed contract that stores hashes of L2->L1 messages in an `AppendOnlyMerkleTree`. Its root (`messageRoot`, also `withdrawRoot` on L1) is included in L2 batch headers.                                               |
| xDomain Message (Cross-Domain Message) | A message sent from one domain (L1) to another (L2), or vice-versa, facilitated by the ScrollMessenger contracts.                                                                                                                     |
| Message Nonce                    | A unique, sequential identifier for a message. For L1->L2 messages, it's the queue index from an `L1MessageQueue`. For L2->L1 messages, it's the index from `L2MessageQueue`. Used for ordering and replay protection.                 |
| Gas Limit (L1/L2 context for messages) | The amount of gas allocated for the execution of a cross-domain message on the destination chain. Specified by the sender and used to estimate fees.                                                                                  |
| FeeVault                         | An L1 contract address where fees collected for L1->L2 messaging (e.g., by `L1ScrollMessenger` or `EnforcedTxGateway`) are sent.                                                                                                       |
| Counterpart (messaging/gateway context) | The corresponding contract on the other layer. E.g., `L1ScrollMessenger`'s counterpart is `L2ScrollMessenger`. `L1ETHGateway`'s counterpart is `L2ETHGateway`.                                                                     |
| **Gateways & Asset Bridging**    |                                                                                                                                                                                                                                       |
| Gateway (L1/L2, ETH, ERC20)      | A smart contract responsible for bridging a specific type of asset (ETH, ERC20, etc.) between L1 and L2. L1 Gateways lock assets and initiate L1->L2 messages. L2 Gateways mint/release assets and initiate L2->L1 messages.        |
| GatewayRouter (L1/L2)            | A contract that acts as a unified entry point for users to interact with multiple specific gateways. It routes deposit (L1) or withdrawal (L2) requests to the correct asset-specific gateway.                                       |
| Standard Gateway (ETH/ERC20)     | Refers to `L1/L2ETHGateway` for native ETH bridging, and `L1/L2StandardERC20Gateway` for generic ERC20 tokens that conform to standards and are represented on L2 by a `ScrollStandardERC20` token.                                  |
| Custom Gateway (ERC20)           | An ERC20 gateway designed for a specific token that might have custom logic, non-standard features, or require a different L2 representation than `ScrollStandardERC20`.                                                              |
| Batch Bridge Gateway             | A specialized gateway system (`L1BatchBridgeGateway`, `L2BatchBridgeGateway`) that allows users to deposit ERC20s/ETH into L1, which are then batched by a Keeper to reduce L1->L2 transaction costs for individual deposits.             |
| Lido Bridge Gateway              | A specialized gateway system (`L1LidoGateway`, `L2LidoGateway`) for bridging Lido's staked ETH tokens (e.g., wstETH) between L1 and L2, managing their specific properties and administrative controls.                                 |
| ScrollStandardERC20              | The standard ERC20 contract deployed on L2 by `ScrollStandardERC20Factory` to represent L1 ERC20 tokens bridged via `L1StandardERC20Gateway`. It includes mint/burn functions controlled by the L2 gateway.                             |
| ScrollStandardERC20Factory       | An L2 contract responsible for deploying instances of `ScrollStandardERC20` tokens using a deterministic address mechanism (CREATE2 via Clones library). Used by `L2StandardERC20Gateway`.                                           |
| **Protocol Operations & State**  |                                                                                                                                                                                                                                       |
| Commit (a batch)                 | The act of a Sequencer submitting an L2 batch's data (or commitment thereof) and header to the `ScrollChain` contract on L1. This makes the batch data available but does not yet confirm its validity.                               |
| Finalize (a batch)               | The act of `ScrollChain` marking an L2 batch as valid and canonical after its ZK proof has been successfully verified. This makes the L2 state transitions in the batch permanent from L1's perspective.                               |
| Finalize (a message)             | For L1->L2 messages, `ScrollChain` marks messages in an `L1MessageQueue` as finalized after the L2 batch containing their execution (or skip status) is finalized. For L2->L1 messages, it means the message has been executed on L1. |
| Finalize (a deposit/withdrawal)  | The completion step of an asset bridging operation on the destination chain. E.g., `L2StandardERC20Gateway.finalizeDepositERC20()` mints tokens on L2 after an L1 deposit.                                                             |
| Drop (a message)                 | An operation on `L1ScrollMessenger` for an L1->L2 message (from `L1MessageQueueV1`) that was finalized as "skipped" by L2 Sequencers. It allows the original sender to reclaim assets or take alternative actions.                     |
| Replay (a message)               | An operation on `L1ScrollMessenger` allowing a user to re-send an L1->L2 message that previously failed execution on L2, potentially with a higher gas limit. A new fee is typically required.                                       |
| Skipped Message                  | In the context of `L1MessageQueueV1`, an L1->L2 message that a Sequencer chose not to include for execution in an L2 batch, often due to capacity or other constraints. Its skipped status is recorded on L1.                         |
| Rolling Hash (L1MessageQueueV2)  | A cryptographic hash maintained by `L1MessageQueueV2`, where each new message's hash is combined with the previous rolling hash. This provides a compact commitment to the entire sequence of messages, used in ZK proofs.           |
| **Other Concepts**               |                                                                                                                                                                                                                                       |
| Predeployed Contract             | A smart contract deployed at a fixed, known address on the L2 network as part of its genesis state. Examples include `L2ScrollMessenger`, `L2MessageQueue`, `L1GasPriceOracle`.                                                     |
| Address Aliasing                 | A mechanism where an L1 address has a corresponding, algorithmically derived L2 address (and vice-versa) to ensure consistent contract addressing across domains, particularly for system contracts like Messengers.                     |
| Enforced Batch Mode              | A state `ScrollChain` can enter if regular Sequencers/Provers are not functioning (e.g., batches not being finalized or messages not being processed in time). In this mode, anyone can permissionlessly commit and finalize a batch with a proof. |
| AppendOnlyMerkleTree             | An abstract contract providing the logic for constructing a Merkle tree where leaves are added sequentially. Used by `L2MessageQueue` to create the `withdrawRoot`.                                                                     |

This glossary should cover the key terms encountered in the Scroll protocol's smart contracts and documentation.
